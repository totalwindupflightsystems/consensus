## What shipped

Consensus is a database-native cognitive architecture for AI agents. It is a
single Go binary — `cmd/consensus` — that carries the whole runtime: one process
serves the REST API, the MCP server, two protocol shims, and two web surfaces,
against either SQLite or PostgreSQL.

If you have not followed the repo, this is the user-visible surface in 0.1.0:

- **A resident agent runtime.** The harness loop polls for tasks on a
  heartbeat, wakes sessions when work arrives, and drains cleanly on
  SIGTERM/SIGINT. Sessions persist their turns in the database, so state
  survives restarts.
- **A REST API** under `/api/v1/*` (chi router) covering sessions, approvals,
  memory, models, and health, with SSE event streams, per-role rate limits, and
  a declared OpenAPI contract pinned by a served-spec parity test.
- **An MCP server** exposing tools, resources, and prompts over JSON-RPC, on
  either SSE (`/mcp/sse`) or stdio (`consensus mcp-stdio`), so MCP-speaking
  agents can drive it without a bespoke client.
- **A CLI** for operating the thing: `serve`, `init`, `migrate`
  (up/down/status), `session`, `approve`/`reject`, `config`, `models`,
  `status`, `memory`, `tool`, `skill`, `completion`, `version` — with
  table/JSON/YAML output and server identity verification before remote calls.
- **Two protocol shims** so existing agent frontends work unmodified: an
  opencode server-protocol adapter (session/config/event translation onto the
  native API) and an H3 shim (health/process/result/sessions/cancel).
- **Both database backends behind one driver interface.** Postgres uses
  LISTEN/NOTIFY for real-time events; SQLite uses a polling bridge.
  Auto-migrations run on startup with drift detection.
- **Human-in-the-loop approvals.** A session can pause on an approval request;
  an expiry cron closes out stale pending approvals. Paired with a **tool
  registry** (`POST /api/v1/tools`, `consensus tool register <name>`) that
  seeds two built-in tools on a fresh install.
- **A cognitive firewall.** Tool output is scanned and quarantined, and
  quarantine events surface on the event bus.
- **Webhook ingestion** at `/webhooks/*` with HMAC signature verification (no
  API key on the ingestion path) and a Go-level rule router that wakes target
  sessions.
- **Two web surfaces in the same binary:** an admin UI at `/ui/` and the
  Chronicle investigation workbench at `/chronicle/`.
- **Release plumbing.** A `v*` tag triggers `.github/workflows/release.yml`,
  which runs GoReleaser against `.goreleaser.yaml` (linux/darwin ×
  amd64/arm64, `CGO_ENABLED=0`, tar.gz + `checksums.txt`, ldflags
  `-X main.version={{ .Version }}`).

History at cut time: 1,947 commits on `main`, with no prior tag. Commit-type
census from `git log --oneline`: feat 114, fix 247, perf 3, docs 101, test 46,
ci 9, chore 225, and zero `BREAKING` markers — which is why the first cut is
0.1.0 rather than a major.

## Install / upgrade

**Upgrade path:** none. `v0.1.0` is the first tag, so there is no `v0.x` to
`v0.1.0` upgrade to document. Fresh installs only.

**Requirement:** Go 1.26. `go.mod` declares `go 1.26.0` with
`toolchain go1.26.11`; the README documents the bare Debian/Ubuntu tarball
route, and an older local toolchain will cause the go command to download the
pinned one on first build.

**Option 1 — build from source (recommended):**

```bash
git clone https://github.com/totalwindupflightsystems/consensus.git
cd consensus
export DEEPSEEK_API_KEY="sk-..."
go build -o bin/consensus ./cmd/consensus/
./bin/consensus init --config consensus.yaml
./bin/consensus serve --config consensus.yaml
```

Build the binary explicitly — `go build -o bin/consensus ./cmd/consensus/` or
`make build`. Do **not** run `go build .` at the repo root: the root package is
`consensus` (a library, not `main`), so that command exits 0 and writes a
5,876-byte `ar` archive instead of an executable (measured in this worktree;
`C-GAP-023` covers the related hazard of running a stale gitignored root
binary). Always check `bin/consensus --version` before running.

`init` also accepts the flag form, `consensus init --db-url <url>` (`--db-url`
is declared on `init` itself; `--config` is a root persistent flag, so it works
here and on every subcommand). The env-only path needs no config file:

```bash
CONSENSUS_DB_URL="sqlite:///tmp/consensus.db" ./bin/consensus init
```

Save the one-time admin key printed by `init`; on first boot `serve` also
prints the bootstrap admin key once. Verify with
`curl http://localhost:8090/api/v1/health`, then open
`http://localhost:8090/chronicle/`.

**Option 2 — containers.** Both compose files exist in the repo
(`docker-compose.yml`, `docker-compose.prod.yml`; the prod file defines
`postgres` + `consensus` services):

```bash
docker compose -f docker-compose.prod.yml up -d --wait
```

or a single container from the published image:

```bash
docker pull ghcr.io/totalwindupflightsystems/consensus:latest
docker run -d \
  --name consensus \
  -p 8090:8090 \
  -v consensus-data:/home/consensus/data \
  -e DEEPSEEK_API_KEY="$DEEPSEEK_API_KEY" \
  ghcr.io/totalwindupflightsystems/consensus:latest
```

Caveat, stated in the README: anonymous GHCR pulls of that image currently
return HTTP 401, so the source build above is the reliable path unless your
GitHub account already has package access. The image tag published by CI is
`latest` plus a per-commit SHA tag; the 0.1.0 GoReleaser assets (tar.gz +
`checksums.txt`) come from the `v0.1.0` tag itself.
