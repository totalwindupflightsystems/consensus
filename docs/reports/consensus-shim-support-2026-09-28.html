Why two surfaces, and why a contract

The shim exists so an existing coding-agent client can point at Consensus and get a real backend — the durable substrate the review called “the highest-leverage idea in the repo”. That promise is worth exactly the fidelity of the two arms it stands between: it must speak the client’s protocol faithfully enough that the client cannot tell, and it must drive the provider’s API richly enough to be useful.

Neither surface is ours. Both are published, versioned, and changed by other people. A drift in either one turns “opencode-compatible” from a claim into a hope — which is why the fix is not a paragraph of intent but a machine-checkable contract plus a refresh procedure: specs/024-shim-support-matrix.md.

The refresh obligation has four parts, and the fourth is the one people skip: pin and record the upstream commit in-repo; make refresh a procedure that derives the surface from the published document and emits a diff report of what changed since our pin; compare declared vs served per path after every refresh; and re-run the upstream suite with its pin attached, because a pass/fail number without a pin is not a measurement.

The near-miss: ACP is a different protocol

The research surfaced a second protocol that shares vocabulary and would be easy to conflate: ACP, the Agent Client Protocol (agentclientprotocol/agent-client-protocol), standardises editor↔agent communication as JSON-RPC 2.0 over stdio, with a curated registry of implementing agents. It is not the opencode server protocol and Consensus does not implement it.

I kept it explicitly out of scope in the contract rather than quietly folding it in — a decision row (REVIEW-CONSENSUS-9) already covers whether to open that door. Naming the boundary is the point: “we speak MCP” and “we speak opencode” must not drift into an accidental claim about cross-vendor interop we never made.

Thinking mode: the rules a harness gets wrong quietly

The rule that matters most

Thinking mode returns its chain of thought as reasoning_content, at the same level as content. Whether that CoT must be handed back on the next request depends on one thing — whether the request carries tools:

  • With tools: the previous turns’ reasoning_content must be passed back, and is concatenated into the context.
  • Without tools: it must not be passed back — and if it is, the provider ignores it.

Control is spelled three different ways depending on the format, and the effort vocabulary maps down onto fewer real levels (minimal and low both land on low; medium, high and xhigh all land on high; max and ultra land on max). Thinking is enabled by default at effort high — so a harness that says nothing is not “off”, it is “high”.

Thinking-mode control, per format (provider docs)
FormatToggleEffort
OpenAI{"thinking":{"type":"enabled|disabled"}} (in extra_body)reasoning_effort
Anthropic{"reasoning":{"effort":"none|low|high|max"}} — none disablesoutput_config.effort
Responses—output_config.effort

And three parameters are accepted with no error and no effect in thinking mode: temperature, presence_penalty, frequency_penalty. That is the kind of silence a harness cannot debug from behaviour — it only surfaces when someone reads the matrix.

Tool calls, and where mid-conversation insertion differs

The tool contract itself is conventional: tools[].function.{name,description,parameters}; the assistant turn returns tool_calls; results return as role tool with a tool_call_id. Tool use in thinking mode is supported from V3.2 onwards.

The non-obvious part is inserting a tool call mid-conversation — which an agent loop does whenever it injects a result the model did not ask for. Support differs by surface:

Mid-conversation insertion
Message typeChat CompletionsAnthropic / Responses
system messagesupportedsupported
tool-call message + resultnot supportedsupported

A harness that only speaks Chat Completions therefore cannot express a whole class of agent behaviour — it has to reach for the Anthropic or Responses surface to do it. And the beta surface (/beta) adds prefix completion, which requires the last message to be role assistant with prefix: true, plus FIM completion (4K max).

The two traps this report exists to prevent

Trap one — failure that looks like success

Today the harness never sends tools, so none of the CoT round-trip rules apply and nothing looks broken. The day provider-native tools go on the wire, a naive implementation loses the model’s earlier reasoning silently — no error, no 4xx, just a dumber agent whose transcripts still look plausible. This is the same shape as the defects that have cost this project most: the billing ledger that wrote nothing while tokens burned, the DELETE that returned 200 and deleted nothing.

Trap two — knobs that do nothing

In thinking mode, temperature, presence_penalty and frequency_penalty are accepted and ignored without an error, and top_p is floored at 0.95 (or fixed at 1.0 outside thinking mode). Any harness that believes it is tuning those knobs against DeepSeek is wrong and has no signal telling it so. Silence is the failure mode.

Two deliberate choices in those rows. First, a matrix cell must carry a reason when it is not supported, so an absent capability is a decision rather than a hole. Second, the pin is part of the measurement: a compatibility number quoted without the commit it was measured at is not evidence, it is folklore.
