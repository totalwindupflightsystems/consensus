Consensus: route-compatible, outcome-broken

A fresh-clone, hands-on review of the DB-native agent runtime — built, tested, served, driven against a real model, and run head-to-head against a 1.5.0 agent harness on identical inputs.

To Bane From thread 4314 Date 3 November 2026 Repo totalwindupflightsystems/consensus Measured at 4e84706 Rows filed at 89dc891

The compatibility surface is real. The agent loop is not. All 48 declared v2 (/api/*) operations answer, and all 34 pinned upstream assertions pass. The same engine could not complete a two-line file-writing task that a minimal harness finished in 8.75 seconds.

Those are not contradictory findings. The suites test that requests are accepted and shaped correctly. Nothing tested that the agent then does the work — and that is exactly where it stops.

The one-line answer

If you move an agent to the v2 API structures and point it at this database, the protocol will hold up and the agent will not finish its work.

The shim answers correctly and completely on the read surface. The moment the agent needs to act — write a file, run a command — the turn suspends into a state that nothing ever resumes. That is not a slow path or an edge case; it is the first tool call of the first real task.

What it is, and whether it builds

Consensus is a database-native agent runtime: the database is the execution engine rather than a persistence layer beside it. Context is a live view, memory is an append-only ledger, and a turn is meant to commit or roll back atomically. It serves REST, MCP, an opencode-protocol shim and an H3 shim from one Go binary.

I cloned the canonical repo fresh, built it with its own Makefile, ran its short suite, and served it on a scratch port. Nothing here is read from documentation.

Why the turn dies

The cause is short enough to quote. handleToolCallDuringPlanning in internal/harness/planning.go (lines 1145–1165) does three things when the model asks for a tool:

  1. Calls tx.Rollback() to close the planning transaction.
  2. Executes UPDATE sessions SET status = 'tool_exec'.
  3. Returns.

The staged tool-call rows are discarded with the transaction that is rolled back, and no tool_requests row is ever written. I confirmed this against the live database: tool_requests = 0, iteration_commits = 0, memory_events = 1. The session is marked as waiting for a tool that does not exist, and nothing can claim work that was never recorded.

Two things then conspire to make it permanent. The claim reaper added for REVIEW-CONSENSUS-1 sweeps only the tasks table (executor.go:917) and never inspects sessions. Meanwhile findActiveSessions (executor.go:988) keeps re-selecting sessions in tool_exec, so the loop spins without ever expiring or failing the row. No terminal state, no notification, no recovery.

A correction to my own first reading. I initially blamed DF-CONSENSUS-48, which had recorded that the async ToolExecutor was never started in production. That fix is genuinely in place — cmd/consensus/main.go:209–211 constructs and starts it. The executor was running correctly and had nothing to do, because no request had been written for it. The rollback is deliberate in the code; what is missing is the insert that was meant to follow it.

Declared against pinned upstream v1.18.33 (7945de20), 188 operations across 162 paths. Filtering out the /experimental/* namespace, which upstream itself treats as unstable, changes the v2 picture not at all:

Two caveats sit inside that green row. Eight v2 operations serve only their error contract — a client that reads through v2 is fine, but one that writes through /api/pty, /api/event, /api/credential or /api/session/{id}/message/{id} still gets a refusal. And three route rows (ROUTE-ADD-052/053/054, the v2 permission and prompt endpoints) are marked failed on the board, so they are gaps rather than coverage.

Route coverage has moved a long way: from 16.5% when the route rows were filed, to 36.2% at the last reading, to 76.1% today. That work is real and it holds up.

Three states worth separating

The reason this review reads as harsh while the numbers read as healthy is that three different questions were being answered by one set of green results.

QuestionAnswerEvidence
Do the v2 routes answer?Yes — 48 of 48coverage artifact at pinned upstream
Do upstream assertions pass?Yes — 34 of 34four pinned suites, zero divergences
Does an agent finish a real task?No — 0 of 1bakeoff: wedge at first tool call

All three can be true at once, and they are. The suites assert that a request is accepted and returned in the right shape. They do not assert that the agent then acts on the response — so a turn that answers 200 message_received and then silently dies satisfies every one of them.

That is the missing third column, and it cannot be closed by more of the same testing. It needs a suite that drives a real task through the shim and asserts the agent's file writes and command output, not the status codes. Such a suite would fail today for a reason the error-shape tests do not model — which is the point of writing it.

What is genuinely good

  • The protocol work is real and recent. 76.1% of 188 declared operations served, all of v2 answering, 17 shim extensions properly declared rather than smuggled in.
  • The upstream harness is honest engineering. Revision pin plus per-file hashes, a transport-only patch restored on a trap, refusal on drift. Most compatibility claims are not tested this way.
  • Fast, clean build. 2-second build, static 28 MB binary, 35-second short suite, 38-table schema. No ceremony.
  • Fails closed on misconfiguration. A missing provider produces a clear error rather than burning iterations against a dead endpoint — that specific mistake is designed out.
  • Cost is first-class. Tokens, iterations and cost are columns on the session row and exposed through the API, not reconstructed from logs after the fact.
  • The board is a real queue. 478 rows, 34 pending with priorities, dispatches happening. Work gets written down here rather than remembered.

What is broken

  • No tool call ever reaches the queue. The rollback discards it before it can be persisted. Every tool-using task wedges at the first call, permanently, with no reaper and no notification.
  • The engine has no hands. A fresh install seeds exactly two tools — list_sessions and demo_approval_gate. There is no read, write, edit, glob or bash. The canonical coding task is not slow here; it is inexpressible. The async executor's dispatch path is additionally a go_native stub that returns a description of itself instead of executing.
  • A session claim has no expiry. The lease added for REVIEW-CONSENSUS-1 does not cover sessions, so criterion "no row can remain claimed forever" is unmet — and was recorded as complete anyway.
  • Eight v2 write paths answer only their error half, which reads as covered in a route table and refuses in a client.
  • Three v2 route rows sit failed — permission and prompt endpoints — so the v2 family is not actually complete at 48.
  • Documented API shape disagrees with the implementation in two ways that cost real time: the message endpoint is singular (/message; the plural 404s) and content must be a plain string, not the content-block array the naming invites.

What I would do next

  1. Fix the insert, not the rollback. Persist the tool request before or independent of the suspend, then re-run the bakeoff unchanged. A two-line task completing is the acceptance test.
  2. Give the engine hands. Seed read, write, edit, glob and bash as real handlers — not stubs — and make the executor path dispatch them. Without this, fixing the wedge only produces sessions that wedge later.
  3. Extend the reaper to sessions so a dead worker cannot strand a session, and add the test that kills a worker mid-claim.
  4. Write the outcome-level suite — drive a real task and assert file writes and command output. This is the third column, and it is the only thing that would have caught the current state.
  5. Then re-run the head-to-head so the comparison has two real legs instead of one.

Items 1 and 2 are the whole ballgame. Everything else in this report is either already working or waiting behind them.

What was not exercised

To be explicit about the boundaries of this review:

  • Postgres backend. Everything above ran on SQLite only. The Postgres path was not built, migrated or driven.
  • The deployed stack. The live container on :8380 was health-checked read-only and left untouched. I did not rebuild or redeploy it, so nothing here speaks to whether the running image matches 4e84706.
  • MCP surface. Not probed in this pass.
  • Multi-turn and multi-tool flows. Impossible to reach — the first tool call wedges — so agent behaviour beyond turn one is unmeasured rather than untested.
  • The 9 experimental operations. Deliberately excluded, on the grounds that upstream treats that namespace as unstable.
  • The bunker QA batteries. Not run; no clean-machine leg is included here.

A passing suite elsewhere is not evidence for any of the above.
