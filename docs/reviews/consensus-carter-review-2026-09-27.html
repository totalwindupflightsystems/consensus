What it is

An agent harness where the database is the runtime: sessions, the message ledger, tool calls, approvals, iteration state and per-call cost are rows, not process memory. The pitch is aimed at the failure mode where an agent framework holds state in a dict, the process dies, and the work is gone.

Shape
one Go binary (consensus serve) + CLI; SQLite for dev, Postgres for prod
Surfaces
REST /api/v1/* (62 paths), MCP over streamable HTTP at /mcp, an opencode-protocol shim (so an existing opencode client can point at it), a web dashboard, and a command-line admin
Model of work
a session gets a goal, a heartbeat loop drives planning iterations, the agent calls tools, everything it learns is appended to memory_events
Money
a billing row per model call with prompt/completion tokens and cost_usd

Docs vs code: the README opens with “Stop building agents on sand. Your database is the runtime.” and a section titled “Your Agent Framework Is Lying To You” — an unusually aggressive claim. It survives contact with the code: the ledger, the cost rows and the restart behaviour are what it says they are. Where docs and code disagree I say so below, and it happened once, in the shim.

What I actually ran

Fresh clone → its own Makefile → scratch port 18300 → real provider → process killed → restarted. Transcripts are verbatim. One caveat up front: my first harness hung because I curled GET /mcp with no timeout — that endpoint holds the connection open per the MCP streamable-HTTP spec, so that was my client's bug, not the server's, and it is why every later call is capped.

MCP — the door an outside agent knocks on

GET  /mcp                        -> 200   (mounts; holds the stream open by design)
POST /mcp  initialize            -> 200
  {"result":{"protocolVersion":"2024-11-05",
             "capabilities":{"tools":{},"resources":{},"prompts":{}},
             "serverInfo":{"name":"consensus","version":"0.1.0"}}}
POST /mcp  tools/list            -> 401
  {"error":{"code":-32000,"message":"Authentication required",
            "data":"API key missing from the MCP initialize request…"}}

Split behaviour. The key I passed in params._meta.authorization is honoured for initialize and rejected for tools/list in the same session. An MCP client that authenticates once at handshake — which is the normal pattern — gets a working server that refuses to list its tools. Filed as a finding; this is the sharpest edge in the review.

Contract fidelity: declared vs served

declared paths   (specs/openapi/bundled.yaml)   -> 62
served paths     (GET /openapi.json)            -> 62
route literals   (internal/api/*.go)            -> 46 + shim mounts

The advertised contract and the running binary agree, path for path. Ten days ago they did not — 60 declared, 59 served, with /mcp 404ing and five paths answering 501. That this now reads 62/62 is the single most reassuring number in the review, because it was fixed in response to exactly this kind of audit.

Not exercised (by name)

  • Postgres backend — everything here is SQLite on one host.
  • The opencode shim as a client: I confirmed it is mounted and that the upstream suite runs against it, but the four pinned upstream suites currently fail 10 assertions (measured by the fleet, not re-run by me), so "opencode-compatible" is not yet true.
  • Concurrency beyond one session — no load probe was run, so every scaling statement below is labelled as a projection.
  • Approvals / human-in-the-loop flow, quarantine, the web dashboard, CLI verbs beyond version/init/serve.
  • Tool execution: I read the code path and saw the ledger rows in the fleet's evidence, but I did not make the agent call a tool myself in this run.

How it compares

Consensus is not competing with agent frameworks so much as with durable runtimes — the layer that keeps state when the process dies.
OptionWhere state livesCrash storyOps weightReach for it when
Consensus this review Your database — sessions, ledger, cost, approvals as rows Restart and query; no replay engine (verified live) One Go binary + a DB You already trust a DB and want the agent's reasoning, tools and cost queryable in SQL next to your product data
Temporal Event-sourced workflow history in its own cluster Replays the event log to reconstruct state Heavy: cluster + workers + a programming model to learn Long-lived, multi-step business workflows where replay semantics are the point
DBOS / Restate / Inngest Durable execution as a library over your DB Checkpoint-and-resume inside your own process Moderate: a library + conventions You want durable execution without adopting a new cluster
LangGraph (+ checkpointers) Checkpoints in a store you pick Resume from the last checkpoint Low to start, grows with the graph You are designing an agent as an explicit graph and want Python-native tooling
opencode / Claude Code / Cursor The session on that machine, usually in memory or a local file Session lost; start over None You want a coding agent in a terminal today

Take: pick Consensus when you want the agent's record to be a first-class, queryable part of your system — cost per turn, what it knew at iteration 3, which tool it called — and you are willing to run a database for it. Pick Temporal when the workflow itself is the product, LangGraph when the graph is the product, and opencode/Claude Code when a single interactive session is. The interesting composition, given the shipped shim: consensus as the durable backend under a coding-agent client, which is exactly the seam that is currently 10 assertions short of working.

How agents hook in

  • REST — 62 served paths, three distinct auth failures, JSON everywhere (verified).
  • MCP — streamable HTTP at /mcp; initialize works and advertises tools/resources/prompts; tools/list currently 401s with the same credential (verified).
  • opencode protocol shim — mounts the opencode server protocol so an existing coding-agent client can point at consensus (mounted and enabled; compatibility currently failing upstream suites).
  • CLI — init, serve, session, memory, approve/reject, mcp-stdio, migrate, models, skill, tool, status.
  • Webhooks in — /webhooks/{source} with signed delivery (added the day before this review; the route was a 404 until then).

Absence, verified by grep: no A2A, no AgentCard, no ACP server implementation. grep -ri 'a2a|agentcard' across internal/, cmd/, specs/ returns CSS badge classes and nothing else. Consensus speaks its own REST plus MCP plus one vendor's protocol; it does not yet speak the cross-vendor agent-to-agent protocol. That is a deliberate-looking omission, not a broken feature, but it is the gap that decides whether a heterogeneous fleet of agents from different vendors can use it as a bus.

From one agent to a thousand

Projection, not measurement. I ran exactly one session. Everything in this section is read from defaults and code, and is labelled as such.

8SQLite max open conns (shipped default was 1 — that single connection wedged the loop under load; fixed)
5 sheartbeat interval
100harness max iterations per session
0lease / visibility-timeout mechanisms found by grep
  • Where it breaks: the pool, not the model. The single-connection default was the P0 that made everything look broken; the failure mode of this class of bug is a loop that waits forever on a transaction. Postgres for real concurrency, and a load probe, are both untested by me.
  • Idempotency is thin: grep -ri idempoten internal/ --include='*.go' excluding tests returns 3 references. Retrying a POST /message after a timeout is not obviously safe, and that is a real gap for a system whose whole promise is "the database remembers".
  • No leases: the lease hits in the tree are semaphores and SAVEPOINTs. There is no visibility-timeout family (claim → lease → ack → redeliver) for tasks, so a worker that dies holding a claim is a manual-cleanup problem, not an automatic one.
  • Cost guard: budget_limit_cents exists as a knob (1000 in the shipped config) and metrics expose total_cost_usd — the metering exists; the enforcement path under load is unverified.

Incident observability

What an operator can see when a turn goes wrong: memory_events (append-only, trigger-enforced for SQLite and Postgres), audit_logs (21 write sites), per-call agent_billing rows, /api/v1/metrics, session last_error, quarantine endpoints, and a per-iteration view.

That is a genuine strength: the two hardest questions in agent operations — what did it know at iteration N and what did that cost — are both SQL queries here, not log archaeology.

The weakness is the same as the strength's blind spot: the observability was the last thing to become true of the process itself. In the last ten days this project has shipped, by its own board: a billing ledger that wrote nothing while real tokens were spent; a DELETE /sessions/{id} that returned 200 and deleted nothing; an unauthenticated SSE stream that leaked another session's contents; and a run of a compatibility suite closed as complete with zero tests executed. All four are fixed or reopened, and each was found by dogfooding rather than by monitoring — which is the honest status: detected afterward, by an adversarial reviewer, not during, by instrumentation.

What I'd add or change

  1. Fix MCP auth precedence first. One credential, one behaviour: if the handshake authenticates the session, tools/list must inherit it. Precedent: MCP streamable-HTTP expects session-scoped auth established at initialize. Cheapest fix with the largest effect on whether an outside agent can use this at all.
  2. Claim leases for tasks and tool calls. Steal Celery's visibility-timeout / Temporal's activity-heartbeat shape: a claim carries an expiry, an unacked claim is redelivered, and a dead worker stops blocking a queue. Precedent: Celery, SQS, Temporal.
  3. Idempotency keys on the mutating surface. POST /sessions and POST /message should accept a client key and be replay-safe; 3 hits of idempotency code is not a policy. Precedent: Stripe-style keys, MCP task ids.
  4. Finish the opencode seam. The shim is the highest-leverage idea in the repo (be the durable backend under clients people already use) and it is 10 upstream assertions away from being a claim you can make.
  5. Publish the grader, not just the grade. This project's most credible artifact right now is its own defect ledger with measured numbers. Shipping the compatibility suite's pass/fail table as a badge a reader can re-run is worth more than any README paragraph.
  6. Consider A2A. If the fleet's agents are going to be heterogeneous, the cross-vendor protocol is a door worth having — after the MCP door closes properly.

Good things

verified live, this session
  • The headline claim is true and I watched it: real provider round-trip (1,323 ms, 1,680/88 tokens), the answer persisted, the cost recorded as 0.00972 USD, and both still readable after killing and restarting the process.
  • Contract honesty: 62 declared paths, 62 served, JSON everywhere, three distinct auth errors that name the actual problem.
  • Build discipline that shows: a 7.8 s build from a cold clone, a single 26.7 MB static binary, go vet clean, 145 test files against 265, 25 migrations, append-only triggers enforced in both database engines.
  • Cost is first-class: a billing row per model call with token classes and a session total, exposed through both the session and system endpoints — most agent runtimes cannot answer "what did that turn cost" without a spreadsheet.
  • The project audits itself: the fixes above did not come from me. They came from its own dogfood, QA, PM and review lanes filing measured defects, and the spec/runtime drift and MCP mount in this report were found by exactly that machinery. A codebase that files this many honest rows about itself is a different animal from one that claims to be finished.

Bad things / rough edges

actually hit, or measured by the project's own instrumentation
  • MCP: authenticated handshake, 401 on tools/list — hit by me, in the first five minutes, following the documented path. An external agent cannot currently use the tool surface.
  • opencode compatibility is measured at 10 failed upstream assertions (34 ran, 24 passed) — and until the day before this review the runner was deleting its own results and mislabelling real divergences as "setup failure", so the number did not exist to be argued with.
  • Alpha edges with teeth, all recent: a dead billing ledger while tokens burned; a DELETE that returned success and deleted nothing; an unauthenticated SSE stream; a shim surface that answered 200 with no key and disclosed host paths; a compatibility task closed on zero executed tests.
  • Advertised-but-absent durability primitives: no leases, no visibility timeouts, ~3 idempotency references. For a project whose thesis is "the state is the product", these are the primitives a serious user will ask for next.
  • Shipped-config traps I hit myself: the runner needs an env var the Makefile makes mandatory; the shipped SQLite pool default was 1 (now 8); the shipped consensus.yaml could not override the model from the environment until recently. Configuration is where this project's paper cuts concentrate.
  • Absence of A2A (grepped, not assumed) — a deliberate-looking but consequential gap.
  • Docs drift happens here too: the review caught a route documented as reading a listener while the code registered something else, and a toolchain requirement the README did not name. Small, but this project earns trust through its exits, not its prose.

Where it could actually be used

  1. Fleet-internal agent backend (now). Its current, real user is the fleet that built it: agents whose sessions, costs and defects are queryable in SQL. That is already working — 40 ticks in 48 h against this board.
  2. As the durable substrate under a coding agent (weeks). Point an opencode-protocol client at it and the client gains a database. Blocked only by the compatibility gap above; the shim already exists.
  3. Agent runs you must be able to explain (months). Regulated or audited settings where "why did it do that, and what did it cost" must be answerable from a record rather than from a transcript someone saved. The append-only ledger is the right shape for this; budgets and approval gates already exist.
  4. Not yet: multi-tenant production without a load probe, and nothing requiring cross-vendor agent interoperability.

Before trusting it: run it on Postgres under concurrent sessions, confirm the MCP surface end-to-end with a real client, and decide the idempotency policy for message delivery.

Verdict

Try it now if the problem you have is "my agent's state and cost live in a process that dies". That problem is solved here, and I verified the solution by killing the process.

Wait if you need to hand it to an external agent today (MCP is split), or to claim a coding-agent compatibility story (10 failed assertions), or to run many concurrent sessions (unmeasured, and the last pool default was catastrophic).

The bar to bet on it: MCP auth consistent across methods; leases plus idempotency keys on the mutating surface; the upstream compatibility suite green or its failures pinned by name; and one published load probe on Postgres. Each is a small, well-scoped change — and the project's own defect ledger says it already knows about all four.

The thing that separates this from the README it criticises: when I found the MCP inconsistency, the fix belonged to a project that had already filed the surrounding class, measured the compatibility gap with real numbers, and reopened a row it had wrongly closed. That is a working quality system, and it is the reason the verdict is "alpha with a strong spine" rather than "another agent framework".
