# SPEC-010: Tools

> **Amended By:** SPEC-011 (Canonical Definitions) — where this spec contradicts SPEC-011, SPEC-011 takes precedence.

> Internal/external tools, JIT registry, autonomous CI/CD, and the plugin system.

## Overview

The Consensus tool system is split into two hemispheres — internal (database-native) and external (TypeScript runtime) — connected by a shared registry, governed by ownership policies, and verified by an autonomous CI/CD pipeline.

---

## Two Hemispheres

### Internal Hemisphere (Database)

- **Runtime**: SQL stored procedures (PL/pgSQL on Postgres, Go-backed equivalents on PocketBase/SQLite)
- **Responsibilities**: Memory management, context paging, view materialization, ledger writes
- **Properties**:
  - Runs inside a DB transaction
  - Zero network latency
  - Fully deterministic
  - Automatic rollback on failure
  - Subject to same RLS policies as all other data access

```sql
CREATE OR REPLACE FUNCTION page_context(
  p_session_id UUID,
  p_page INT
) RETURNS TABLE (chunk TEXT, relevance REAL) AS $$
  SELECT content, vec <=> (SELECT embedding FROM sessions WHERE id = p_session_id)
  FROM context_chunks
  WHERE session_id = p_session_id
  ORDER BY vec <=> (SELECT embedding FROM sessions WHERE id = p_session_id)
  LIMIT 20 OFFSET (p_page - 1) * 20;
$$ LANGUAGE sql STABLE;
```

Internal tools never leave the database. They are the fastest, safest, most auditable tool type.

### External Hemisphere (Sandboxed Execution)

- **Runtime**: Sandboxed subprocess or HTTP endpoint, managed by the Go binary
- **Responsibilities**: Web scraping, API calls, any network-bound or I/O-bound operation
- **Properties**:
  - Stored in database (`tool_files` table)
  - Executed in sandboxed subprocess with configurable permissions
  - Network access granted per-tool
  - Timeout enforced by the agent loop
  - Results written back to database

External tools are the bridge to the outside world. They are stored in the database, versioned in the registry, and executed by the harness.

## JIT TypeScript Package Registry

### Concept

Agents write TypeScript code at runtime and insert it into the `custom_agent_tools` table. Other agents discover and import this code instantly — an internal npm registry generated by AI.

### Schema

```sql
CREATE TABLE custom_agent_tools (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    creator_session_id UUID NOT NULL REFERENCES sessions(id),
    name              TEXT NOT NULL,
    language          TEXT NOT NULL CHECK (language IN ('javascript', 'typescript', 'sql', 'python', 'go')),
    source_code       TEXT NOT NULL,
    parameter_schema  JSONB NOT NULL DEFAULT '{}',
    approved          BOOLEAN NOT NULL DEFAULT false,
    status            TEXT NOT NULL DEFAULT 'draft'
                      CHECK (status IN ('draft', 'testing', 'active', 'deprecated')),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(name)      -- Globally unique tool name (prevents namespace collision)
);
```

### Tool Execution

The Go binary fetches tool code dynamically from the database and executes it in a sandboxed subprocess:

```go
func ExecuteExternalTool(ctx context.Context, tool CustomAgentTool, params map[string]any) (*ToolResult, error) {
    // Write tool code to temp file
    tmpFile := filepath.Join(os.TempDir(), fmt.Sprintf("consensus-tool-%s.js", tool.Name))
    os.WriteFile(tmpFile, []byte(tool.Code), 0600)

    // Execute in sandboxed subprocess with timeout
    ctx, cancel := context.WithTimeout(ctx, 30*time.Second)
    defer cancel()

    cmd := exec.CommandContext(ctx, "deno", "run", "--allow-net", tmpFile)
    output, err := cmd.Output()
    os.Remove(tmpFile)

    if err != nil {
        return &ToolResult{IsError: true, Output: err.Error()}, nil
    }
    return &ToolResult{IsError: false, Output: string(output)}, nil
}
```

The sandbox runtime (Deno subprocess) is optional — tools can also be native Go handlers or HTTP endpoints.

### Lifecycle

1. Agent A writes a tool → `INSERT INTO custom_agent_tools (name, code, language) VALUES ('zillow_scraper', $1, 'typescript')`
2. Agent B discovers the tool via `SELECT name FROM custom_agent_tools`
3. Agent B requests tool execution → harness fetches code from DB, executes in sandbox
4. If Agent A updates the tool → `UPDATE custom_agent_tools SET code = $2 WHERE name = 'zillow_scraper'`
5. Agent B's next invocation pulls the updated code automatically

No rebuild. No deploy. No restart. The database IS the package registry.

## Tool Ownership & Governance

### Registry Schema

```sql
CREATE TABLE tools_registry (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name              TEXT NOT NULL UNIQUE,
    description       TEXT NOT NULL,
    hemisphere        TEXT NOT NULL CHECK (hemisphere IN ('internal', 'external')),
    parameter_schema  JSONB NOT NULL DEFAULT '{}',
    handler_type      TEXT NOT NULL CHECK (handler_type IN (
                        'sql_function', 'http_endpoint', 'go_native', 'subprocess'
                     )),
    handler_ref       TEXT NOT NULL,
    owner_session_id  UUID REFERENCES sessions(id),
    status            TEXT NOT NULL DEFAULT 'active'
                      CHECK (status IN ('active', 'testing', 'deprecated', 'disabled')),
    enabled           BOOLEAN NOT NULL DEFAULT true,
    requires_approval BOOLEAN NOT NULL DEFAULT false,
    rate_limit_per_min INT,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- tool_files: Tool source code is stored in custom_agent_tools.source_code (SPEC-011 §5).
-- Binary/large file artifacts use the tool_files table from SPEC-003 §2.12.
```

### Row-Level Security: Ownership Enforcement

```sql
CREATE POLICY enforce_ownership ON custom_agent_tools
  FOR UPDATE USING (
    current_setting('consensus.session_id')::UUID = (
      SELECT creator_session_id FROM custom_agent_tools WHERE id = custom_agent_tools.id
    )
  );
```

**Rule**: Agent A cannot modify Agent B's tool. Period.

If Agent A needs a change to Agent B's tool, Agent A opens an internal "Jira ticket":

```sql
INSERT INTO task_queue (task_type, payload, requested_by)
VALUES ('tool_modification_request', '{
  "tool_name": "zillow_scraper",
  "requested_change": "Add retry logic for 429 errors",
  "requestor": "agent-a"
}', 'agent-a');
```

Agent B picks up the task, makes the change, and resolves the ticket.

## Autonomous CI/CD Pipeline

### Flow

```
Agent B writes feature
        │
        ▼
UPDATE tool_files SET code = $1, version = version + 1
        │
        ▼
AFTER UPDATE trigger fires
        │
        ▼
Tool status: active → testing
        │
        ▼
Background sandbox compiles TypeScript + runs tests
        │
    ┌───┴───┐
    │       │
  PASS    FAIL
    │       │
    ▼       ▼
  active   testing persists
            │
            ▼
          Stack trace → test_results table
            │
            ▼
          Wake Agent B with error log
```

### Implementation

```sql
CREATE OR REPLACE FUNCTION trigger_tool_ci() RETURNS TRIGGER AS $$
BEGIN
  UPDATE tools_registry SET status = 'testing' WHERE id = NEW.tool_id;
  PERFORM pg_notify('tool_updated', NEW.tool_id::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tool_files_after_update
  AFTER UPDATE ON tool_files
  FOR EACH ROW EXECUTE FUNCTION trigger_tool_ci();
```

```sql
CREATE TABLE test_results (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tool_id     UUID NOT NULL REFERENCES tools_registry(id),
  version     INT NOT NULL,
  passed      BOOLEAN NOT NULL,
  output      TEXT,
  run_at      TIMESTAMPTZ DEFAULT now()
);
```

### Sandbox Execution

The background sandbox:

1. Pulls tool files from `tool_files` where `tool_id` matches the updated tool
2. Compiles TypeScript with `deno check`
3. Runs associated test files
4. On pass → `UPDATE tools_registry SET status = 'active' WHERE id = $1`
5. On fail → `INSERT INTO test_results (tool_id, version, passed, output) VALUES (...)`
6. On fail → `INSERT INTO task_queue (task_type, payload) VALUES ('test_failure_alert', ...)` to wake the owning agent

The tool is not available to other agents while in `testing` status. The CI/CD pipeline is the gate.

## Database-Native Skills (Plugin System)

### Concept

Skills are database rows. INSERT a new row = every authorized agent instantly "knows" the plugin exists. No file system. No deployment. No plugin directory.

### Schema

```sql
CREATE TABLE skills_registry (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name              TEXT NOT NULL UNIQUE,
    metadata          JSONB NOT NULL,
    instructions      TEXT NOT NULL,
    linked_tool_ids   UUID[] NOT NULL DEFAULT '{}',
    enabled           BOOLEAN NOT NULL DEFAULT true,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- `metadata` — Lightweight summary (~100 tokens): skill name, description, when to use
- `instructions` — Full SKILL.md content (can be thousands of tokens): detailed workflow, examples, constraints
- `linked_tool_ids` — Array of tool IDs this skill depends on (references `tools_registry.id`)

### Progressive Disclosure

Agents only see metadata during normal operation:

```sql
SELECT name, metadata FROM skills_registry;
```

This costs ~100 tokens per skill — feasible to include in every agent's system prompt.

When the agent determines it needs a skill:

```sql
SELECT instructions FROM skills_registry WHERE name = 'excel_generator';
```

The massive instruction set is injected into the agent's context window only when needed.

### Load Function

```sql
CREATE OR REPLACE FUNCTION load_skill(p_skill_name TEXT) RETURNS TEXT AS $$
  SELECT instructions FROM skills_registry WHERE name = p_skill_name;
$$ LANGUAGE sql STABLE;
```

### Plugin Ecosystem

Because skills are just rows:

- Adding a skill = `INSERT INTO skills_registry (...)`
- Updating a skill = `UPDATE skills_registry SET instructions = $1 WHERE name = $2`
- Deprecating a skill = `UPDATE skills_registry SET metadata = metadata || '{"deprecated": true}', enabled = false WHERE name = $1`
- Discovering skills = `SELECT name, metadata FROM skills_registry WHERE enabled = true`

No plugin directory. No marketplace. No build step. The database is the ecosystem.

## Event-Driven Plugins

### Concept

Agents write to their own domain tables. AFTER INSERT triggers pick up rows and push work to the async task queue. The agent doesn't need to know about OAuth, rate limits, or external API details.

### Example: Orders Plugin

```sql
CREATE TABLE local_orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  data        JSONB NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending',
  created_at  TIMESTAMPTZ DEFAULT now()
);
```

The agent simply inserts orders:

```sql
INSERT INTO local_orders (data) VALUES ('{"item": "widget", "qty": 5, "customer": "Acme Corp"}');
```

The trigger handles the rest:

```sql
CREATE OR REPLACE FUNCTION trigger_order_sync() RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO task_queue (task_type, payload)
  VALUES ('external_api_call', json_build_object(
    'action', 'create_order',
    'order_id', NEW.id,
    'data', NEW.data
  )::text);
  NEW.status := 'processing';
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER local_orders_after_insert
  AFTER INSERT ON local_orders
  FOR EACH ROW EXECUTE FUNCTION trigger_order_sync();
```

The external worker picks up the task, handles OAuth tokens, rate limits, retries, and writes the result back:

```sql
UPDATE local_orders SET status = 'completed' WHERE id = $1;
```

### JSON Schema Validation

Only well-formed triggers fire:

```sql
-- Using sqlite-jsonschema on PocketBase
SELECT jsonschema_validate(
  '{"type":"object","required":["item","qty"],"properties":{"item":{"type":"string"},"qty":{"type":"integer"}}}',
  data
) FROM local_orders;
-- Returns NULL if valid, error message if invalid

-- Using CHECK constraints on Postgres
ALTER TABLE local_orders ADD CONSTRAINT valid_order_data
  CHECK (jsonb_matches_schema('{
    "type": "object",
    "required": ["item", "qty"],
    "properties": {
      "item": {"type": "string"},
      "qty": {"type": "integer", "minimum": 1}
    }
  }', data));
```

Bad data is rejected at the constraint level. The trigger never fires for malformed input. The agent receives a clear constraint violation error.

### Benefits

| Benefit | How |
|---|---|
| Decoupling | Agent doesn't need to know about external API details |
| Reliability | External worker handles retries, rate limits, OAuth |
| Auditability | Every state transition is a row in a table |
| Testability | Insert test data → trigger fires → verify task_queue entry |
| Simplicity | Agent just writes to its own table |

## Tool Resolution Order

When an agent needs to perform an action, the runtime resolves tools in this order:

1. **Internal hemisphere** — Check for a SQL stored procedure (fastest, zero network)
2. **Skill-linked tools** — If a skill is loaded, check `linked_tool_ids` for pre-approved external tools
3. **JIT registry** — Query `custom_agent_tools` for agent-authored tools
4. **Runtime built-ins** — Harness-level utilities (fetch, log, etc.)

This order ensures agents prefer deterministic, transactional tools first, and fall back to external tools only when necessary.

## Summary

| Layer | Storage | Execution | Governance |
|---|---|---|---|
| Internal tools | SQL (DB) | DB transaction | Schema ownership |
| External tools | `tool_files` (DB, SPEC-003 §2.12) | Sandboxed subprocess | Agent ownership + RLS |
| JIT tools | `custom_agent_tools` (DB) | Sandboxed subprocess | Creator agent owns |
| Skills | `skills_registry` (DB) | Progressive disclosure | DB row = plugin |
| Event plugins | Domain tables (DB) | Trigger → task_queue | JSON Schema validation |
| CI/CD | `test_results` (DB) | Background sandbox | Status gate (testing → active) |

Everything is a database row. Everything is governed by SQL. The database is the registry, the package manager, the CI/CD system, and the plugin marketplace.
