# `.gitignore` and `.ignore` Management (Portable)

> **The core tension**: Git cleanliness wants files hidden. AI agents need files visible. The `.ignore` file is the bridge.

Load this skill when:
- Adding new `.gitignore` entries
- Deciding whether a file should be committed or ignored
- Debugging why an AI agent "can't see" a file it should be able to read
- Setting up `.gitignore` for a new Axiom-managed repo

## The AI Visibility Problem

OpenCode (the AI coding engine) uses `.gitignore` patterns to determine which files to **hide from its own tools** — `read_file`, `grep`, `glob`, and directory listings all respect `.gitignore`. This means:

- A gitignored file is **invisible to the AI agent**. It cannot read it, search it, or reason about it.
- This is usually correct (you don't want the AI drowning in `node_modules/`).
- But sometimes you *want* a file gitignored (ephemeral, not for git) yet *visible to the AI* (needed for debugging or verification).

**The solution**: The `.ignore` file at the repo root uses the same gitignore syntax and lets you override OpenCode's hiding behavior. A `!pattern` entry in `.ignore` **un-hides** a gitignored path, making it visible to OpenCode while keeping it out of git.

Reference: https://opencode.ai/docs/tools/#ignore-patterns

```
# .gitignore — keeps file out of git
regression-evidence-*.log

# .ignore — makes it visible to OpenCode anyway
!regression-evidence-*.log
```

## What to Gitignore (MUST)

### Build Artifacts and Bytecode
```gitignore
__pycache__/
*.pyc
*.pyo
*.pyd
*.class
*.o
*.so
dist/
build/
*.egg-info/
```
**Rationale**: Reproducible from source. Large. No value to AI or git history.

### Tooling Caches
```gitignore
.pytest_cache/
.mypy_cache/
.ruff_cache/
.hypothesis/
.tox/
.coverage
htmlcov/
```
**Rationale**: Regenerated on every run. Can be large. AI does not need raw cache internals.

### Virtual Environments
```gitignore
.venv/
venv/
env/
.env/
node_modules/
.opencode/node_modules/
```
**Rationale**: Installed from lock files. Enormous. Never useful to AI or git.

### Secrets and Environment Files
```gitignore
.env
.env.*
!.env.example
*.pem
*.key
credentials.json
secrets.yaml
```
**Rationale**: Secret leak risk. MUST gitignore. `.env.example` is the exception — it's a template with no real secrets.

### IDE and Editor State
```gitignore
.DS_Store
.idea/
.vscode/settings.json
*.swp
*.swo
.project
.classpath
```
**Rationale**: Machine-local. Causes noise in diffs. Not useful to AI.

### Generated Outputs (Reproducible)
```gitignore
specs/ALL.md          # merged specs output — regenerated by scripts/merge_specs.py
specs.md              # same
```
**Rationale**: If a file can be regenerated deterministically from committed sources, it should not be committed. Exception: contract snapshots (see below).

### Ephemeral Test Evidence
```gitignore
regression-evidence-*.log
regression-summary-*.md
regression-assertions-*.jsonl
ui-lane-evidence/
```
**Rationale**: Regenerated on every test run. Raw output is too large for git history. Findings should be summarized into `.memory-bank/` instead (see Memory Bank section below).

### Runtime State
```gitignore
.axiom/state/
*.pid
*.sock
*.lock          # runtime locks only — NOT package manager lock files
_tmp/
```
**Rationale**: Per-machine, per-process ephemeral state. Never meaningful in git.

### Ephemeral Work Item Artifacts
```gitignore
.memory-bank/work-items/loop-runs/
.memory-bank/work-items/test-*/
.memory-bank/work-items/WI-*/
.memory-bank/work-items/e2e-*/
```
**Rationale**: Test-generated or loop-run artifacts that must not pollute durable memory bank knowledge.

## What NOT to Gitignore (MUST commit)

### Contract Snapshots
| File | Why |
|------|-----|
| `openapi.json` | API contract for consumers. Not a build artifact — it IS the contract. Gitignoring it breaks API consumers and contract drift detection. |
| `asyncapi.json` | Same reasoning for event-driven APIs. |

### Package Manager Lock Files
| File | Why |
|------|-----|
| `package-lock.json` | Reproducible Node.js builds |
| `bun.lockb` | Reproducible Bun builds |
| `yarn.lock` | Reproducible Yarn builds |
| `poetry.lock` | Reproducible Python builds |
| `Pipfile.lock` | Reproducible Pipenv builds |
| `Cargo.lock` | Reproducible Rust builds (for applications) |

**Rationale**: Lock files are the reproducibility guarantee. Gitignoring them means every `npm install` can produce a different dependency tree.

### Environment Templates
```gitignore
!.env.example   # explicitly un-ignore — it's a template, not a secret
```

### Spec Files
Even if a spec file is generated by a tool (e.g., from a PRD), commit it. Specs are contracts. The generation tool is the source of truth for *how* it was produced; the spec file is the source of truth for *what* the system must do.

### Hand-Crafted or Expensive Test Fixtures
If a fixture took significant effort to create or cannot be regenerated cheaply, commit it. Only gitignore fixtures that are auto-generated on every test run.

### Durable Memory Bank Knowledge
`.memory-bank/` contains long-term project context, decisions, and agent knowledge. **Do not gitignore the entire `.memory-bank/` directory.** Only gitignore the ephemeral subdirectories (loop-runs, test-generated artifacts).

## The `.ignore` File — Decision Framework

When you add a new `.gitignore` entry, ask:

```
Does the AI agent ever need to read this file?
├── No  → Gitignore it. Done.
└── Yes → Gitignore it AND add !pattern to .ignore
          so OpenCode can still see it.
```

### Decision Table

| File type | Gitignore? | Add to `.ignore`? | Rationale |
|-----------|-----------|-------------------|-----------|
| `node_modules/` | ✅ Yes | ❌ No | Too large; no AI value |
| `.venv/` | ✅ Yes | ❌ No | Too large; no AI value |
| `__pycache__/` | ✅ Yes | ❌ No | Binary bytecode; no AI value |
| `.pytest_cache/` | ✅ Yes | ❌ No | Internal cache; no AI value |
| `.hypothesis/` | ✅ Yes | ⚠️ Maybe | AI may want to inspect found examples for test analysis |
| `regression-evidence-*.log` | ✅ Yes | ✅ Yes | AI needs to read evidence for verification |
| `regression-summary-*.md` | ✅ Yes | ✅ Yes | AI needs summaries for verification |
| `regression-assertions-*.jsonl` | ✅ Yes | ✅ Yes | AI needs assertion data for analysis |
| `.axiom/state/` | ✅ Yes | ✅ Yes | AI may need runtime state for debugging |
| `axiom-runtime-test/` | ✅ Yes | ✅ Yes | AI needs to inspect test environment |
| `axiom-template/` | ✅ Yes | ✅ Yes | AI needs to read template for generation |
| `.env` | ✅ Yes | ❌ No | Secrets — NEVER expose to AI context |
| `openapi.json` | ❌ No | N/A | Contract — must be committed |
| `*.lock` (package manager) | ❌ No | N/A | Reproducibility — must be committed |
| `.env.example` | ❌ No | N/A | Template — must be committed |

### Flowchart

```
New file or directory to manage
         │
         ▼
  Contains secrets?
  ├── Yes → MUST gitignore. NEVER add to .ignore. Stop.
  └── No
         │
         ▼
  Reproducible from source / regenerated on every run?
  ├── No  → Commit it (do not gitignore)
  └── Yes
         │
         ▼
  Is it a contract snapshot (openapi.json, lock file)?
  ├── Yes → Commit it (do not gitignore)
  └── No
         │
         ▼
  Gitignore it. Then ask:
         │
         ▼
  Does the AI agent need to read this for
  debugging, verification, or analysis?
  ├── No  → Done. Gitignore only.
  └── Yes → Also add !pattern to .ignore
```

## Memory Bank vs Raw Test Results

Raw test output and durable knowledge serve different purposes:

| Artifact | Where it lives | Gitignored? | AI visible? |
|----------|---------------|-------------|-------------|
| Raw pytest output (10k lines) | `regression-evidence-*.log` | ✅ Yes | ✅ Yes (via `.ignore`) |
| Assertion dumps | `regression-assertions-*.jsonl` | ✅ Yes | ✅ Yes (via `.ignore`) |
| Hypothesis examples | `.hypothesis/` | ✅ Yes | ⚠️ Maybe |
| **Summarized findings** | `.memory-bank/work-items/<ID>/` | ❌ No | ✅ Yes |
| **Durable decisions** | `.memory-bank/decisionLog.md` | ❌ No | ✅ Yes |

**Pattern**: Run tests → capture raw output (gitignored, AI-visible via `.ignore`) → summarize findings into `.memory-bank/` (committed, always AI-visible) → AI reads summaries in future sessions.

The AI doesn't need 10,000 lines of raw pytest output. It needs a 50-line summary of what passed, what failed, and what patterns emerged. Write that summary to `.memory-bank/`.

## Checklist: Adding a New `.gitignore` Entry

- [ ] **Is this file reproducible from source?** If yes, it's a gitignore candidate. If no, commit it.
- [ ] **Does it contain secrets?** If yes, MUST gitignore. NEVER add to `.ignore`.
- [ ] **Is it a contract snapshot?** (`openapi.json`, lock files, `.env.example`) → Do NOT gitignore.
- [ ] **Is it too large to be useful in AI context?** (`node_modules/`, `.venv/`) → Gitignore and keep hidden.
- [ ] **Does the AI need to see it for debugging or verification?** → Gitignore AND add `!pattern` to `.ignore`.
- [ ] **Should findings from this file be preserved long-term?** → Summarize to `.memory-bank/` (committed).
- [ ] **Update `.ignore` if needed.** After adding to `.gitignore`, check if a corresponding `.ignore` entry is required.
- [ ] **Add a comment** to `.gitignore` explaining *why* the entry exists (especially non-obvious ones).

## Checklist: Setting Up `.gitignore` for a New Repo

- [ ] Start from a language-appropriate base (e.g., GitHub's gitignore templates).
- [ ] Add secrets patterns: `.env`, `.env.*`, `!.env.example`, `*.pem`, `*.key`.
- [ ] Add virtual environment patterns for the repo's language stack.
- [ ] Add build artifact patterns for the repo's build system.
- [ ] Add IDE patterns: `.DS_Store`, `.idea/`, `.vscode/settings.json`.
- [ ] Add ephemeral test evidence patterns (regression logs, assertion dumps).
- [ ] Add runtime state patterns (`.axiom/state/`, `_tmp/`).
- [ ] Create `.ignore` at repo root (even if empty) to document the override mechanism.
- [ ] Add `!` entries to `.ignore` for any gitignored paths the AI needs to see.
- [ ] Verify `openapi.json` and lock files are NOT in `.gitignore`.
- [ ] Add comments to non-obvious entries explaining why they are ignored.

## Anti-Patterns

| Anti-Pattern | Why It's Bad | What to Do Instead |
|---|---|---|
| Gitignoring `openapi.json` | Breaks API contract for consumers; hides drift | Commit it — it's a contract, not a build artifact |
| Gitignoring lock files | Breaks reproducible builds; different deps on each install | Commit all package manager lock files |
| NOT gitignoring `.env` | Secret leak risk — credentials end up in git history | Always gitignore `.env` and `.env.*` |
| Forgetting to update `.ignore` | AI agent can't see files it needs for debugging/verification | After every `.gitignore` addition, ask: "Does AI need this?" |
| Committing raw test output | Bloats git history; stale evidence misleads future agents | Gitignore raw output; summarize findings to `.memory-bank/` |
| Gitignoring all of `.memory-bank/` | Destroys durable agent knowledge; agents lose context between sessions | Only gitignore ephemeral subdirs (`loop-runs/`, `test-*/`, `WI-*/`) |
| Gitignoring spec files | Specs are contracts — hiding them breaks traceability | Commit all spec files, even auto-generated ones |
| Adding secrets to `.ignore` | Exposes secrets to AI context | Never add secret-containing paths to `.ignore` |
| No comments in `.gitignore` | Future agents/developers can't understand why entries exist | Add a one-line comment above each non-obvious entry |
| Wildcard patterns that are too broad | May accidentally ignore important files | Test patterns with `git check-ignore -v <file>` before committing |

## Verifying Your `.gitignore` and `.ignore`

```bash
# Check if a specific file is being ignored (and why)
git check-ignore -v path/to/file

# List all ignored files in the repo
git ls-files --others --ignored --exclude-standard

# Verify a file is tracked (not ignored)
git ls-files path/to/file

# Test that openapi.json is NOT ignored
git check-ignore -v openapi.json   # should print nothing (not ignored)

# Test that .env IS ignored
git check-ignore -v .env           # should print the matching rule
```
